# Detailed depth

Read this when the depth is **detailed** (*detailed · بالتفصيل*). It replaces the fixed What / Why / How block; every step still covers what, why and how.

## Choosing methods
For each step pick the **2–3 methods** that fit *that* topic, and vary them as topics change. Never run the same pair of methods through every step.

| Method | Fits a step that… |
|---|---|
| Worked example with real numbers, or an input → output trace | computes or transforms something |
| Analogy from daily life | introduces a new abstract idea |
| Alternatives table — option · strength · why not | involves a real design choice |
| What breaks without it | looks optional but isn't |
| Line by line | is one dense line or an unfamiliar construct |
| Term box — term · meaning | introduces several terms at once |
| Common mistakes | uses an easy-to-misuse API or tool |
| Before / after | changes a layout, format, document or existing code |
| Question and answer | has a counter-intuitive point |
| Summary first, then detail | is long |
| Flow — the whole pipeline in one line, the current part in bold | is one stage of a process |
| Check your understanding (answer hidden) | teaches something the rest depends on |

## Code
Line by line scatters attention. Show short, simple code **whole** and explain it as one idea. Walk line by line only through a dense line or an unfamiliar construct, and never in two steps in a row. Prefer a trace, a worked example or "what breaks without it" when they show the point better.

## Shape of a detailed step
```
## Step 2: matching answers

<one-line summary of the step>

<code block, whole>

<method 1 — e.g. an input → output trace as a small table>
<method 2 — e.g. an alternatives table>
<one duck line, if it teaches>
```

## Pitfalls
- Detailed means *deeper*, not *longer everywhere*: a trivial step still gets one line.
- An alternatives table needs real alternatives someone would pick; don't invent straw men.
- A worked example must use numbers that were actually run or checked.
